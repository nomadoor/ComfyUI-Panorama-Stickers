# ADR 0040: `MOGE_GEOMETRY` の透視投影の列を深度のグリッドで運ぶ

## Status

Accepted（2026-10-10）（1 フレームとピンホールでない点は GLB のままにすることを、オーナーが決めた。2026-10-10）

## Date

2026-10-10

---

## 背景

オーナーの主な使い方は、動画のフレーム（IMAGE バッチ）にコアの Run MoGe Inference（MoGe-3、`moge_3_vitl`・`moge_3_vitg`）を掛けた `MOGE_GEOMETRY` である。今はフレームごとにグリッドのメッシュの GLB を書くので、ADR 0039 の前の `DA3_GEOMETRY` mono と同じ問題（書き出しの時間、temp の量、エディタの約 5 fps）がある。ADR 0039 は `MOGE_GEOMETRY` を次の候補としていた。

コードで確かめた事実：

- コアの `MoGeInference` は常に `intrinsics`（フレームごと、正規化した座標）を出す。`force_projection` が真（既定）なら、点をコアの `depth_map_to_point_map(depth, intrinsics)` で作り直す。画素の中心は `((x + 0.5) ÷ W, (y + 0.5) ÷ H)`。偽なら推論した点のままで、`depth` と `K` から点は戻らない。
- `MoGePanoramaInference` は 1 枚の画像しか受けない。パノラマの `MOGE_GEOMETRY` は 1 フレームである。
- MoGe はフレームごとに独立に推論し、焦点距離・z のずれ・メトリックの尺度もフレームごとに求める。

## 決定

ADR 0039 を書き換えず、別の ADR にする（0039 は `DA3_GEOMETRY` の決定として Accepted で、範囲の違う決定を足すと本文を直すことになるため）。

- 透視投影（`intrinsics` あり）で 2 フレーム以上、全フレームの点がピンホール（keep の画素の点がコアの `depth_map_to_point_map` と一致し、z が 0 より大きい）の入力は、ADR 0039 と同じ深度のグリッドで運ぶ。深度は点の z。MoGe の正規化した `K` は、Python が画素の番号の `K` に直してメタに書く。エディタの JS と GLSL は DA3 のまま使い、MoGe 用の式を持たない。
- 残す画素（keep）は、`moge_grid_mesh` と同じ `triangulate_grid_mesh` の部品を同じ順に組み立てて求め、test で `moge_grid_mesh` に一致させる。
- そのほか（パノラマ、1 フレーム、ピンホールでない点）は今の GLB のまま。黙って形を変えない。
- 出力の描画は `moge_grid_mesh` のまま。中身の箱は keep の画素の点から作り、メッシュにしない。
- ちらつき（フレームごとの独立な推論）は入力の性質として残し、均さない。

## 考えた別案

| 案 | 選ばなかった理由 |
|---|---|
| xyz の点のマップ（RGB32F） | 点そのものを運ぶのでどの入力（パノラマ、`force_projection` が偽）でも正確で、GLSL に逆投影の式を写さない。代わりに深度の 3 倍の帯域：1080p で 1 フレーム約 24.9 MB（深度は約 8.3 MB）、4K で約 99.5 MB（約 33.2 MB）。1080p × 314 フレームで約 7.8 GB になり、temp の上限（5 GiB）を超える。keep を値の `> 0` で表せず、別の表し方も要る |
| パノラマも深度のグリッドにする | ERP の向きの式（`spherical_uv_to_directions` と画素の中心）を GLSL に写すことになる。コアのパノラマは 1 フレームなので速さの問題がない |
| 1 フレームも深度のグリッドにする（道は 1 つになる） | 静止画の色が元の解像度の PNG から H.264 のプロキシ（長辺 2048 以下）に変わり、見た目が粗くなる。1 フレームなら GLB でも遅くない。オーナーの決定で GLB のまま |
| ピンホールでない点をエラーにする | `force_projection` を切った使い方を止めてしまう。GLB に戻せば遅いだけで描ける。オーナーの決定で GLB に戻す |
| 時間の平滑化 | 使う人のデータを変えることになる |

## Consequences

- MoGe の動画は、DA3 mono と同じく書き出しが速くなり、temp は 1080p × 314 フレームで約 2.6 GB と MP4、エディタは深度のグリッドの速さで再生する。色はプロキシからで、ADR 0039 と同じ差がある。
- 同じ `MOGE_GEOMETRY` でも、条件で `kind` が `depth_grid` と `mesh` に分かれる。エディタは `kind` で読み分けるだけで、形は同じになる（色は深度のグリッドではプロキシから来る）。
- 判定（`depth_map_to_point_map` の作り直しと、keep の画素ごとのノルムの比較）の分だけ、書き出しに手間が増える。1080p × 60 フレームの実測で、判定が 4.1 秒（うち keep が 2.8 秒）、深度のファイルの書き込みが 2.9 秒だった。判定は入力ごとに 1 回だけ行い（共有のキャッシュ）、ノルムの比較は 2 乗の和で行う（同じ条件）。
- GLB に戻した入力は、理由（パノラマ、1 フレーム、ピンホールでない）を実行ごとに 1 回ログに出す。1 つの `MoGeInference` の出力はフレームの間で混ざらず、混ざるのはつないだ辞書だけで、そのときも入力全体が GLB になる。
