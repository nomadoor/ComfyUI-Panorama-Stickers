# ADR 0037: World の 3D をどこで、何で描くか

## Status

Accepted（2026-10-09。試作の結果は判断の規則の 1 行目に当たった。実 GPU のブラウザとの一致は最初の milestone で確かめる）

## 背景

Panorama Studio の出力は、ノードがサーバーで描く。背景・Sky・ペイントは PyTorch で出力の画素ごとの光線から直接標本化し
（ADR 0034）、World の中身（`scene` の中身と `world` の Sticker）は、自作の PyTorch のレンダラー（`core/mesh_render.py`・
`world_render.py`、`splat_render.py`）で「色と光線の長さ」の層にして、奥行きで合成する（`docs/render-contract.md`）。
エディタは同じ Scene をブラウザの three.js と Spark で描く。

このレンダラーは、開発の初めに「コアの RenderSplat に合わせて純粋な torch で自作する」と決めたものである（ADR は無い）。
スプラットにはコアに揃える相手があったが、メッシュにはなかった（コアの RenderMesh も、光源・PBR・アニメーションを持たない）。
その結果、メッシュは描けない部分を切り捨てて描いている：

- 光を当てない（unlit）。光源の概念が Scene に無い。
- 材質は最初の 1 つのテクスチャだけ。係数（baseColorFactor など）、テクスチャの変換、sampler、mip を使わない。
- glTF のアニメーション・skin・morph を読まない（コアの読み手が捨てる）。Timeline を持つのに、モデルは動かない。

オーナーは次を求めている：glTF のアニメーション、光（光を当てない選択も含む）、複数の材質と PBR、レンズの歪みなどの
カメラの表現、4DGS へ進める道、どの環境でも同じ出力、そしてエディタで見た見た目がそのまま出力になること。

## 決めること

World の 3D のうち**メッシュ**を、出力のためにどこで、何で描くか。あわせて、出力の画素から光線を作る**カメラの型**を、
どの描き方でも成り立つ形にするか。

決めないこと（変えない、または別の ADR）：

- 背景・Sky・ペイントの描き方と、層を奥行きで合成する契約（`SceneContent.render(view, index, device)` が色と光線の長さを
  返し、`over_by_depth` で畳む）。
- スプラットの描き方（今の経路、コアの RenderSplat に準拠）。4DGS のエディタでの表示と形式は別の ADR。
- 光源・アニメーションの clip・カメラのレンズの値を、状態 v2 のどこに持つか（別の ADR と spec）。ERP の背景を環境光
  （IBL）に使うかも、その ADR で決める。

## 満たすべき条件

1. **どの環境でも同じ出力。** 同じ Scene は、GPU の機種・OS・CUDA か CPU かによらず、許容差（下の「一致の測り方」の
   「環境の間」）の中で同じ画像になる。GPU のドライバやグラフィックスの API の有無で、描けるものが変わらない。
2. **許容差つきでエディタの表示と出力が一致する。** 一致は、決まった場面をエディタと出力で描いた画像の差と、アニメーションと
   材質の式の数値の差で守る。次の差は意図して残し、test の対象から外す：
   - スプラットとメッシュが入り組む画素。出力は画素ごとに一つの奥行きで層を畳む近似で、エディタは Spark がメッシュの
     深度に対してスプラットごとに混ぜるので、原理的に一致しない。
   - 今の spec が意図して残している差（`docs/threejs-spark-integration.md` の「ノードの出力との差」）。
   - 下の「D の設計の規則」で意図して残すと書いた差（BLEND のメッシュどうしが交わる所、レンズの歪みの場面の許容差、
     点光源の影の縁）。
3. ブラウザを開いていない実行（API）でも同じ出力になる。
4. 出力は ERP（360° と 180°）と透視投影。動画の全フレーム（数百枚、4K〜8K の ERP）を描く。3D のモデルが入った場面の
   1 フレームに許す時間は、NVIDIA の GPU（RTX 4070 Ti 程度）で 8K の ERP が 3 秒以内、4K が 1 秒以内（オーナーが決めた。
   影ありもこの中に収める）。
5. **カメラの型**：出力の画素から光線を作る式を、カメラの型として一か所に持つ。透視投影と ERP に加えて、主点のずらし、
   レンズの歪み（Brown–Conrady の放射方向と接線方向の歪み）と魚眼（等距離射影から始める）を、同じ枠に足せる。ERP には
   歪みを掛けない。背景・Sky・World（メッシュとスプラット）のどの層にも、同じ光線で正確に同じ歪みがかかる（描いた画像を
   後から歪める近似にしない）。被写界深度（光線を画素の中で散らす）を後から足せる。そのコストは光線の本数に比例する
   （8K で 16 本なら約 5 億本）。
6. 動く環境：Windows・Linux・WSL2 の NVIDIA GPU で速く動く。CPU でも CUDA と同じ出力で動く（test で守る。速さは静止画と
   4K の短い動画の範囲で、8K の動画は時間の単位になる）。AMD（ROCm）と Apple Silicon（MPS）は同じコードが動く設計にするが、
   確かめていない。壊れていると分かった環境では、理由を出して断る（黙って劣化させない）。利用者に pip で入らない部品を
   求めない。
7. 依存は最小で、pip で入る。CUDA の拡張のビルドを使う人に求めない。ライセンスが商用利用を妨げない。
8. 描くもの：glTF のアニメーション（node・skin・morph）、PBR の材質（金属・粗さ、法線、遮蔽、発光、
   `KHR_texture_transform`、sampler、TEXCOORD_1）、透明（`alphaMode` の OPAQUE・MASK・BLEND、`doubleSided`）、光源
   （平行・点・スポット。光を当てない選択も）、影（選べる）、テクスチャの mip と sampler（wrap の REPEAT・CLAMP・MIRRORED、
   filter の NEAREST と LINEAR）、色空間（層の中は線形で照明し、層を返す境界で sRGB にする。
   tone mapping は three.js と同じく無し）。
   描かないもの：three.js の上級の材質（透過、クリアコート、シーン、異方性など）と、エディタの GLTFLoader は読めるが出力が
   読めない拡張（`KHR_draco_mesh_compression`・`EXT_meshopt_compression`・`KHR_texture_basisu`）。これらは、置く時点で
   理由を出して断る。黙って似せない。`KHR_mesh_quantization` は、コアの読み手が読めるなら受け付ける。
9. 8K の 1 フレームのメモリが、今の見積もり（`docs/runtime-resources.md` の `_render_memory`）に収まるか、見積もりに
   足して数えられる。
10. 4DGS（時刻ごとに変形したスプラット）を、同じ層の契約に乗せて描ける。

## 調べた事実

- コアのサーバー側の 3D の描画は、すべて純粋な torch の自作である。RenderSplat（透視投影だけ、解像度は最大 2048、色は
  基本色だけ、奥行きを合成用に出さない）、RenderMesh（光線を飛ばし、透視投影 1 視点、ヘッドライトでクレイを描く）、
  SAM3D の rasterizer。PBR・skin・morph・アニメーションは無い。コアの glTF の読み手は skin と morph を捨て、アニメーションを
  読まない。光源の型 `LOAD3D_LIGHT_INFO`（平行・点・スポット）を足す PR（Comfy-Org/ComfyUI #16327）が開いている（未マージ）。
  その RenderLight はスタジオの場面を光線で描くもので、任意のメッシュのレンダラーではない。コアは、サーバーの描画を純粋な
  torch で作る方向に進んでいる。
- Load3D はサーバーで何も描かない。実行するときにブラウザが撮った画像をアップロードし、ノードはそれを読むだけである。
  ブラウザで描いたものを取り込む PR（#14044）はマージされずに閉じ、新しい Load3DAdvanced（#14316）は状態だけを渡して
  描画を下流に任せる。
- コアの任意の依存 `comfy-angle`（ANGLE）と `PyOpenGL` で GPU の GLES を使えるが、ANGLE は OS ごとに別のグラフィックスの API
  （Windows は D3D11、Linux は Vulkan、macOS は Metal）で描く。Linux 版は Vulkan のバックエンドだけを持ち、WSL2 では pip で
  入らない dzn（Mesa の Vulkan on D3D12）が無いと GPU に届かない。オーナーの WSL2 には dzn が無い。
- ヘッドレスの Chromium で three.js を動かす実例はあるが、GPU を使うにはフラグとドライバの条件があり、ドライバの更新で
  壊れた報告と、ANGLE のメモリリークの報告がある。
- nvdiffrast と、元の diff-gaussian-rasterization は非商用のライセンスである。PyTorch3D・Kaolin・gsplat は CUDA の
  ビルドか組み合わせごとの wheel が要る。wgpu-py（pygfx の土台）は WSL を対応外と明記している。bpy（Blender）は
  Python 3.13 専用で数百 MB、GPL。
- 今の torch のメッシュの描画は、光線と三角形の交差で、約 400 万面を 4K の ERP に 0.2 秒、約 1670 万面を 0.4 秒で描く
  （RTX 4070 Ti、`docs/legacy-baselines.md`）。コストは（三角形, 画素）の組の数で決まる。アニメーションする GLB は普通
  1 万〜30 万面で、頂点が毎フレーム変わる分の追加（skin の行列と面の平面の再計算）は小さい。光を当てない 8K は 1 フレーム
  0.5〜2 秒程度と見込める。影とテクスチャの mip は、まだ無い。
- 今の torch の描画は、CUDA と CPU の差が、旧ノードの場面で 0.001/255 未満、Sky の直接標本化の場面で平均 0.0003/255 未満・
  最大 0.01/255（`docs/legacy-baselines.md`）。CPU は、4K・約 400 万面のメッシュを 2.9〜3.4 秒で描く。10 万面の GLB の 8K は、
  光を当てないで 1 フレーム 3〜6 秒、光を当てると 1〜2 秒増える見込み。
- 今の一次光線の速さは、三角形ごとに写りうる画素の範囲を求める絞り込み（`_erp_bounds`・`_perspective_bounds`）による。
  これは原点が一つの光線の束にしか効かない。原点が画素ごとに違う光線（影の光線、透明の再探索）には BVH が要る。コアには
  純粋な torch の BVH と、最も近い交点・何かに当たるかの探索（`nodes_mesh_postprocess.py` の `_build_triangle_bvh`・
  `_closest_hit_rays_bvh`・`_any_hit_rays_bvh`）があるが、4M 光線ごとに分けて約 2 GB を使い、スタックを超えた枝を黙って
  捨てる。8K（約 3350 万本）の影の光線をこれで飛ばすと、RTX 4070 Ti でも 1 フレーム数秒、CPU では分の単位になる。
- three.js の影は shadow map（光源から深度を描き、bias と PCF のぼかしで比べる）で、縁の柔らかさと接地の浮きはその設定で
  決まる。正確な影の光線は硬い影を出すので、エディタと一致しない。

## 考えた案

### A. サーバーでもヘッドレスの Chromium で three.js と Spark を動かす

採らない：エディタと同じコードで描くので一致は最も高いが、Chromium（約 170 MB）のダウンロードという新しい依存と
ネットワークの手順が要る。GPU が使えるかは環境とドライバに強く依存し、CPU に落ちると 8K の数百フレームは実用にならない。
条件 1（どの環境でも同じ）と 6（ドライバに左右されない）を満たさない。

### B. ブラウザで描いて送る（Load3D と同じ）

採らない：実行中に上流のノードが作る MESH・SPLAT・VIDEO を描けず、ブラウザの無い実行では動かない。8K の ERP の
動画の全フレームを送る量も現実的でない。コアもこの方向を採らなかった。

### C. EGL と GLES 3.0 で、GPU のラスタライザを持つ

利点：three.js と同じ GLSL ES 3.00 のシェーダの源を、エディタと出力で使える（材質と光の決まりを二重に持たない）。
採らない：ANGLE でもシステムのドライバでも、OS と GPU ごとに別の API とシェーダのコンパイラで描くので、出力が環境ごとに
少しずつ違い、ドライバの更新で壊れうる（条件 1・6）。WSL2 では pip で入らない部品が要るか、環境ごとに context の作り方を
分けることになる。CPU だけの環境と GPU の無い CI では動かない。cubemap を描いて画素ごとの光線で引く形なら歪みは
画素ごとに効くが、cubemap の再標本化の分の近似が入る。

### D. torch の光線方式のレンダラーを育てる

今のレンダラー（画素ごとの光線と三角形の交差）を、条件 8 の範囲まで育てる。同じコードが CUDA・ROCm・MPS・CPU で動き、
ドライバにもグラフィックスの API にも依存しない。光線を出力の画素から作るので、カメラの型（ERP・透視投影・レンズの歪み・
魚眼・被写界深度）は、光線の作り方を変えるだけで、背景・Sky・World のどの層にも正確に同じに効く。コアの向き（純粋な torch）
とも同じ。
負うもの：
- 材質と光の決まりを、エディタ（three.js）と出力（Python）に二重に持つ。一致は、決まった場面の画像の差と、式の単体の
  数値の差で縛る（今の状態の評価関数の parity と同じやり方）。
- 影とテクスチャの mip を自前で作る。影は、光源からのカメラの型（平行光源は平行な光線の束、点とスポットは透視）で、
  一次光線と同じ絞り込みの経路で深度を 1 枚描き、three.js と同じ bias と PCF で比べる（光線方式のまま。エディタの
  shadow map と同じ原理なので一致の test に乗る）。点光源は全方向なので、光源の位置からの ERP の深度 1 枚で描く（three.js の
  6 面とは縁の形が少し違う。意図して残す差）。shadow map の範囲（平行光源の left・right・top・bottom・near・far）、大きさ、
  bias・normalBias・PCF の半径は、光源の値として状態が持ち、エディタと出力が同じ値を読む（内容に合わせて自動で決めない）。
  正確な影の光線は、後から「高品質」の選択として足せる。
- 速さは光線方式のまま出す。三角形を塗る方式に変えて速さを得ることはしない（条件 5 を壊すので）。そのため、交差の探し方
  （面の絞り込み、BVH など）で速さを出せるかを試作で確かめる。

## 推奨

D を採る。条件 1（どの環境でも同じ）、5（カメラの型）、6（ドライバに左右されない）を満たすのは D だけである。D が負う
「決まりの二重化」は、この repo がすでに状態と評価関数で行っている parity の仕組みで縛る。

## D の設計の規則（採るなら spec に書く）

- **カメラの型**：出力の画素から光線（原点と向き）を作る関数を、カメラの型ごとに一か所に持つ（今の `core/math.py` の
  `ray_directions` を広げる。レンズの値は `Projection` に入れるので、`render_frame` の `cache` の光線の使い回しの規則は
  変わらない）。背景・Sky・ペイント・World の層は、すべてこの光線を使う。
  - レンズの歪みは、出力の画素（歪んだ像）から歪みの無い像の座標へ戻す式を光線の前に置く。Brown–Conrady の順方向には
    閉じた逆が無いので、反復で解く。反復の回数と初期値を JS と Python で同じにし、数値の parity の fixture で縛る。
    多項式が折り返す（単調でなくなる）半径より外の画素は、無効（`bg_color`）にする。
  - エディタには今、後処理のパスが無い。歪みの無い像を、レンズの値から求めた余白（overscan。FOV と解像度を広げる）付きで
    描き、歪みを後処理のシェーダで掛けるパスを足す。後処理は再標本化でぼけが入るので、歪みの場面の一致は許容差を別に置く
    （下の「一致の測り方」）。
  - スプラットの窓の大きさと形は、今は投影ごとに解析的な Jacobian（透視と ERP）で求めている。新しいカメラの型に乗せるため、
    光線の場（隣の画素の光線との差）から数値的に求める形に変える（別の差分）。
- **glTF の読み手**：一か所に持ち、出力が使う。コアの `read_accessor` などを使い、コアが捨てる部分を足す：animation
  （STEP・LINEAR・CUBICSPLINE、四元数の slerp、複数の clip）、skin（`inverseBindMatrices`、8 影響まで）、morph（sparse の
  accessor、node の `weights`）、材質（条件 8）。pygltflib などの純 Python の読み手は JSON と accessor を読むだけで、
  評価（本体）は減らないので、依存にしない。
- **アニメーションの評価**：Playwright で three.js に GLB を読ませ、時刻 t の node の行列と skin の後の頂点を書き出し、
  Python の評価と 1e-5 以内で一致することを、JS と Python が共有する fixture で確かめる。四元数ではなく行列と頂点で比べる
  （q と −q は同じ回転）。fixture の場面に、morph の重みと、CUBICSPLINE の clip の端（three.js は端で clamp）を入れる。
- **材質と光**：three.js の `MeshStandardMaterial` と光源の式（BRDF、光の減衰、スポットの角度）、影の比較
  （`shadowmap_pars_fragment` の bias と PCF）を Python に移す。式は単体の数値の test で three.js の実装と比べ、場面は画像の
  差で比べる。
- **精度**：交差と光の式は、グローバルな精度の設定（`torch.backends.cuda.matmul.allow_tf32` など。ほかの custom node や
  利用者が変えうる）に左右されない演算（要素ごとの積和、または呼び出しの中で TF32 を明示的に切る）で書く。
- **透明**：今の探索は画素ごとに最も近い交点を一つだけ残す。
  - MASK：当たった点のアルファが `alphaCutoff` 未満なら、その画素だけその先を探し直す（通常 1〜3 回）。
  - BLEND：three.js と同じ近似を取る。不透明の層を作った後、BLEND のメッシュごとに最も近い交点を求め、不透明の奥行きより
    手前なら奥のメッシュから順に重ねる（メッシュの単位で並べ、深度は書かない）。メッシュどうしが交わる所は three.js と
    同じく崩れる（意図して残す差）。
  - `doubleSided` が偽なら裏面を捨てる。両面のときの照明の法線は、three.js と同じく視線の側に向ける。MoGe などの両面の
    描き方は保つ。
- **テクスチャの mip**：three.js と同じ等方の trilinear。当たった画素の uv を画像の隣の画素の uv と差分して LOD を出し、
  mip の段を線形に混ぜる。隣が別の面・別の物・空なら片側の差分。Sky の異方の ripmap（`_sample_filtered`）はメッシュには
  使わない。
- **光源の型**：コアの `LOAD3D_LIGHT_INFO`（PR が入れば）と互換にできる形にする。
- **三つの描き分け**：光を当てない（今の見た目。写真から作った素材向け）、光を当てる、影あり、を Scene の設定として選べる。
- **速さ**：一次光線と shadow map は今の絞り込み（`_erp_bounds`・`_perspective_bounds`）で描く。原点の散る光線（MASK の
  再探索、後日の影の光線）だけ BVH を使う。コアの BVH を `core_adapters.py` の規則の下で使うか、写しを持つかは、その
  ときに決める（コアの BVH はスタックを超えた枝を黙って捨てるので、使うならそこを確かめる）。
- **メモリ**：shadow map と透明の層の分を `_render_memory` の見積もりに足す。
- three.js の版はコアに合わせて上がる（ADR 0031）。上がるたびに、一致の test の基準を焼き直して差分を見る。

## 一致の測り方

- **エディタと出力**：投影は透視投影（エディタは ERP を描けない）。1024 × 1024、hFOV 60°、`ray_directions` と同じ画素の
  中心の規則に Camera を合わせる。場面は、光を当てないテクスチャ（市松、遠近あり）、PBR と平行光源 1 つ、影、skin のある GLB
  の t = 0.5 秒、レンズの歪みのある透視投影。指標は今の基準画像と同じ（平均の絶対誤差と、8/255 を超える画素の割合）。
  縁を 1 画素削った内側で、平均 ≤ 1/255、8/255 超 ≤ 0.5% を暫定の合格とする。光を当てない場面と当てる場面を分けて出す。
  レンズの歪みの場面は、エディタの後処理の再標本化のぼけがあるので、低周波の素材で測り、許容差を別に置く（試作で決める）。
  エディタ側は `tests/browser/` の Playwright で撮る（キャンバスを 1024 × 1024、`deviceScaleFactor: 1` に固定する）。基準は、
  GPU の無い CI でも同じ画像が得られる llvmpipe（ANGLE の Vulkan を Mesa の lavapipe に乗せる）で焼く。llvmpipe は、Chromium に
  `--use-angle=vulkan --enable-features=Vulkan` を渡し、実行する環境に Mesa の Vulkan の ICD があるときだけ選ばれるので、test は
  WebGL の renderer 名（`UNMASKED_RENDERER_WEBGL`）を確かめ、llvmpipe でなければ失敗させる（黙って別の基準と比べない）。
  Mesa と LLVM の版が上がると画像が動きうるので、three.js の版と同じく、上がるたびに焼き直して差分を見る。GPU の実装との差は、
  milestone ごとにオーナーの実 GPU のブラウザで確かめる。
- **環境の間**：同じ場面を CUDA と CPU で描き、平均 ≤ 0.01/255、8/255 を超える画素 ≤ 0.01%（交点の当たり外れの反転を
  拾う）。GPU の無い CI でも回す。

## 試作で確かめること

1. **速さ**：skin のある GLB（約 10 万面）を 8K の ERP で 100 フレーム。光を当てない・光を当てる・平行光源 1 つの影あり
   （shadow map）の三つ。GPU のメモリのピークも取る。CPU は 4K で 10 フレーム。合否は条件 4 の許容時間（8K で 3 秒、4K で 1 秒）。
2. **一致**：上の「エディタと出力」の場面のうち、光を当てないテクスチャと、PBR と平行光源 1 つ（式を移した試作で）。
3. **環境の間**：同じ場面の CUDA と CPU の差。

## 判断の規則

| 試作の結果 | 決定 |
|---|---|
| 速さ・一致・環境の間の基準を満たす | D を採る（Accepted。MPS・ROCm は確かめていないと記す）。仕様の差分（カメラの型、光、アニメーション、3D ファイルの投入）に進む |
| 光を当てない・光を当てるは満たすが、影ありだけ速さを満たさない | D を採る。shadow map の大きさと PCF のタップを詰める試作をする。影は既定で切る |
| 光を当てない場面でも速さを満たさない | 交差の探し方を BVH などで作り直す試作をする。それでも満たさなければ、許容時間をオーナーと見直す（三角形を塗る方式には変えない） |
| 一致の基準を満たさない | 差の出る式を特定して直す。直せない差は、意図して残す差として spec に書くか、描かないものに移す |

## 試作の結果（2026-10-09、試作の branch `proto/renderer-spike`、merge しない）

すべて実測。GPU は RTX 4070 Ti（計測の前の nvidia-smi で、オーナーの ComfyUI を含めて使用率 14〜91%、メモリ 6904〜7303 MiB（6.7〜7.1 GiB）。
最良の値ではない）。場面は、
コードで作った skin のある筒（102,400 面、骨 20 本、1 頂点あたり重み 4 つ、毎フレーム torch で線形の skin）と地面。

**速さ**（1 フレームの平均 / p95。許容時間は NVIDIA の GPU で 8K が 3 秒、4K が 1 秒。CPU の行は許容時間の対象外で、条件 6 の
「CPU でも同じ出力で動く」の参考）

| 条件 | 光なし（今の描き方） | 光なし＋mip | 光あり | 影あり（shadow map 2048） |
|---|---|---|---|---|
| CUDA 4K・100 フレーム | 0.060 / 0.067 | 0.108 / 0.140 | 0.155 / 0.183 | 0.192 / 0.228 |
| CUDA 8K・100 フレーム | 0.214 / 0.225 | 0.423 / 0.483 | 0.569 / 0.631 | 0.682 / 0.738 |
| CUDA 8K・全画素に面が当たる部屋・30 フレーム | 0.433 | 0.826 | 1.146 | 1.407 / 1.466 |
| CPU 4K・10 フレーム | 0.686 | 1.313 | 1.727 | 1.998 |
| CPU 8K・2 フレーム | 2.89 | — | — | 7.12 |

- 時間を決めるのは面の数ではなく、当たった画素の数と（三角形, 画素）の組の数。面を 10 万から 30 万に増やしても
  変わらなかった。頂点が毎フレーム変わる追加の費用はほぼ無い（範囲の計算は CUDA で 2〜4 ms）。
- 8K・影ありの内訳：一次光線 0.17 秒、shadow map の描画 5 ms、参照 0.10 秒、陰影 0.40 秒（微分のための隣の画素の光線
  0.15 秒、trilinear 0.10 秒、BRDF 0.07 秒）。torch の GPU のメモリのピークは 8K で 2751〜2891 MiB（2.69〜2.82 GiB、1 画素あたり約 86〜90 B。reserved は 3048〜3254 MiB）。
- この試作の範囲（不透明、一次光線、shadow map）では、BVH と影の光線は要らなかった。MASK の再探索は確かめていない。
- 場面はテクスチャ 1 枚（base color）で、重なりは前後 2 層ほど（組の数は当たった画素の約 3 倍）。法線・金属粗さ・遮蔽・発光の
  map を足すと、trilinear が 1 枚あたり 8K で約 0.1 秒（部屋で約 0.2 秒）増え、法線 map には接空間の計算も要る。部屋・影ありの
  1.4 秒に 5 枚分を足しても 3 秒に収まる見込みだが、髪や服などの重なりの多い実際の素材では組の数が増える（測っていない）。

**エディタとの一致**（1024²、hFOV 60°、縁を 1 画素削った内側。平均 / 8/255 を超える画素）

この WSL2 ではヘッドレスの Chromium が GPU を使えなかったので、three.js r184 をソフトウェアの二つの実装（SwiftShader、
llvmpipe）で描いて比べた。縁を削らない全画素でも、光なし 0.264 / 0.308%、PBR 0.0052 / 0.0054%、影 0.0069 / 0.0089%
（SwiftShader と）で、削り方で合格を作っていない。

| 場面 | SwiftShader と | llvmpipe と |
|---|---|---|
| 光なしの市松（mip、線形の空間で補間） | 0.443 / 0.52% | 0.273 / 0.0003% |
| 同じ場面を今の描き方で（sRGB のまま双線形、mip なし） | 16.5 / 45% | 16.4 / 45% |
| PBR の球とトーラス、平行光源 1 つ | 0.018 / 0.0006% | 0.00015 / 0% |
| 地面と PCF の影 | 0.008 / 0.009% | 0.00005 / 0% |
| （参考）SwiftShader と llvmpipe の three.js どうし、光なし | 0.48 / 0.52% | — |

SwiftShader の光なしだけ 0.5% をわずかに超えた。three.js どうし（SwiftShader と llvmpipe）の差と同じ大きさで、エディタの
実装の違い（拡大した線の上で uv の補間が画素の一部分ずれる）である。そこで一致の test の基準は llvmpipe で焼く（全場面で
合格）。
今の光を当てない出力は、エディタと平均 16/255 ずれている（sRGB のまま補間し、mip が無いため）。

**環境の間**（CUDA と CPU、同じ入力）：光なし（mip）0.00058/255、PBR 0.000005/255、影あり 0.000007/255、skin のある ERP 2048 の
新しい経路（mip・光・影）で ≤ 0.0005/255。どれも 8/255 超 0%、当たり外れの反転 0。今の描き方（光なし、mip なし）だけ、
ERP 2048 で 8/255 超が 0.0003〜0.0004%（数画素）出た。今の `_base_color` の折り返し（`uv - floor(uv)` の後に端で延ばす双線形）
で、整数のすぐ近くの uv が反対側の端に飛ぶためで、基準の中だが、新しい経路に切り替える理由の一つになる。グローバルの TF32 を有効にすると、PBR で 8/255 超が 0.049%、反転が 6 画素
出て基準を超えた。

**判断**：判断の規則の 1 行目（速さ・一致・環境の間の基準を満たす）に当たる。ただし一致は、ソフトウェアの描画（llvmpipe）に
対して確かめたもので、オーナーの実 GPU のブラウザとはまだ比べていない。これを Accepted の後の最初の milestone の確認事項にする。

**試作で分かった、設計の規則に足すこと**

- 微分（mip の段と `geometryRoughness` に要る）は、2×2 の画素の組の相手の光線を、同じ三角形の平面と交差させて値を外挿して
  求める（GPU の helper の画素と同じ考え方。隣が別の面でも働き、画像全体の一時の領域が要らず、ERP でも同じに働く）。
- `geometryRoughness`（画面上の法線の微分を粗さに足す項）は差の最も大きい項。ERP の出力でどの軸で測るかを spec で決める。
- three.js r184 の直接光は multiscatter の DFG の表（16 × 16）を使う。表を写し、three.js の版が上がるたびに写し直す。
  sRGB の変換の指数は three.js と同じ 0.41666 にする。
- shadow map：片面の材質は裏面だけを描く（shadowSide）。normalBias の法線は、頂点ごとに正規化してから補間した値。
  PCF は r184 と同じく、Vogel の円盤の 5 回の参照 × 2×2 の比較で、回転は出力の画素の座標から作るノイズ（IGN）で決める。
- 光を当てない出力も、線形の空間での補間と mip に切り替える（今の出力はエディタと一致していない）。
- TF32 の防御（精度の規則）は必須。今の `mesh_render._intersect` の行列積がこの設定に左右される。

**確かめていないこと**：オーナーの実 GPU のブラウザとの一致（NVIDIA のテクスチャの補間とは、もう少し差が出る見込み）、
実際の GLB の読み手とアニメーションの評価、MASK と BLEND、点光源とスポット、8K の動画全体のメモリ（他の層を含む）、
MPS と ROCm。


## Consequences

- 決まれば、3D ファイルの投入（保留中）は、この描き方を前提にして仕様を書く。
- 今の「光を当てない・最初の材質だけ・アニメーションしない」の決まりは、描き分け（光を当てない／当てる／影あり）と
  条件 8 の範囲に置き換えて spec から書き直す。
- カメラの型（レンズの歪みを含む）を状態 v2 に持つ形は、別の spec の差分で決める。
- `docs/runtime-resources.md` の見積もりに、shadow map と透明の層の分を足す。
