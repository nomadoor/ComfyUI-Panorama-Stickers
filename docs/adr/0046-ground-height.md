# ADR 0046: 原点はパノラマを撮った点のまま、地面の高さを別に持つ

## Status

Accepted（2026-10-17）

## Date

2026-10-17

---

## 背景

ADR 0045 で視点を一つにし、試作（`proto/single-viewpoint`）でオーナーが触った。原点に立って見回すこと自体は良いが、次の問題が出た。

- 目の高さが原点と同じ 0 で、地面のグリッド（World の XZ 平面 y = 0、`docs/threejs-spark-integration.md` の「空間の表示」）を真横から見るので消える。
  3D の中に立っている実感がない。
- 新しく置く物は、視点から見ている向きの線の上に置く（`docs/editor-interaction.md` の「置く向き」）。水平に見ていると目の高さの正面に浮き、
  手前に向いたギズモの軸が点につぶれる。
- 完全な World では、原点にあまり価値がない（オーナー）。

原点は今、パノラマを撮った点として使われている：Camera が無いときの ERP は原点から撮る（ADR 0029、`nodes.py` の `ORIGIN_CAMERA`）、
MoGe と DA3 の単眼で持ち上げた空間の原点は撮ったカメラ、Pose handoff は「Camera が原点から動かなければ `sky`」で決める（ADR 0030、
受け取る側の `nodes.py` の判定）。一方、グリッドと置く物は、同じ原点を地面として使っている。パノラマを撮った点と地面が同じ高さにあることが、
上の問題の原因である。

オーナー：「3D とパノラマを完璧にリンクさせるのは至難の技」。一致するのは撮った点から見たときだけである。

## 決定

- **座標は変えない。原点はパノラマを撮った点のまま。** Camera が無いときの ERP の出力、`scene` の置き場所、Pose handoff の判定、`sticker_state`、
  `PANO_SCENE` の数珠つなぎは変わらない。既存の状態の出力が変わるのは、下の `port` の 3D の Sticker だけ。
- **地面の高さ（`ground`、World の y の値）を状態に一つ持つ。** 新しい状態の初期値は -1.6（原点の 1.6 下）。値は保存し、開くたびに測り直さない
  （オーナー：毎回床が変わるのは気持ち悪い、対処療法）。
  - 1.6 は保存して変えられる値の初期値にとどまり、規則がこの数に依存することはない。単位は入力素材のまま（ADR 0023）なので、
    素材によっては意味を持たない。そのとき困るのはグリッドと新しく置く物の位置だけで、目で見て直せる。
  - 変えるときは、地面にしたい面を一度クリックする（「ここを地面にする」。当たった点の y を保存する）。形は「空間と視点」の spec で決める。
  - `ground` は欠けてよい。欠けているときは、上流の Scene があれば上流の `ground`（`PANO_SCENE` の層の状態に載る）、無ければ -1.6 として読む。
    既存の状態も新しい状態も同じ規則で読み、状態の古さで振る舞いが変わる隠れたモードを作らない。
  - 正規化は既定の値を書き込まない（`docs/scene-state-v2.md` の `sceneStateText` の規則と同じ）。書き込むと、エディタを開いて閉じただけで
    キャッシュが外れ、下流は上流を受け継げなくなる。使う人が地面を変えたときだけ値が入る。
  - `ground` が効くのは、グリッド、エディタで置く物の位置、ノードが置く 3D の `port` の Sticker の位置（下）である。
- **グリッドと軸は `ground` の高さに描く。** 内容が無い（Sky だけの）ときのグリッドの大きさは spec で決める。
- **新しく置く 3D の物は、正面の地面の上に置く。** 視点の水平の向きに、全体が収まる距離だけ離し、底を `ground` に付ける。視点の向きは動かさない。
- **ノードが置く 3D の `port` の Sticker も、同じ規則で地面の上に置く**（オーナー、2026-10-17）。入口によって置き場所の規則を二つにしない。
  今の「原点の前の目の高さ」（`nodes.py`）を置き換え、Python と JS の両方を変えて `tests/fixtures/place_3d/fit.json` の parity を広げる。
  既存のワークフローで、動かしていない `port` の 3D の Sticker は出力の位置が地面まで下がる（オーナーが承認）。
  - 移行：影響するのは、状態に `port` の 3D の Sticker の記録が無いワークフローである（ノードは記録が無いと実行のたびに置き直し、`state_json`
    には書かない。`nodes.py` の `_world_port_sticker`）。エディタで一度でも動かして記録があるものは変わらない。前の位置に戻したいときは、
    エディタで動かせば記録が残る。実行結果の警告「placed in front of the origin to fit the view」は、地面に置いたことを言う文に直す。
    ノードの `PANO_SCENE` の下流では、ノードは上流の層の `ground` も読む。
  - 置く式は今の「外接球を視線の上に収める」に高さを足すだけでは済まない：底を地面に付けるには回した箱の一番下が要り（外接球の下端では平たい物が
    浮く）、向きを水平にすると球が視線から外れるので収まる距離の求め方も変わる。何も無いときの仮の置き場所にも底が無い。式は spec で決め、
    `tests/fixtures/place_3d/fit.json` の場面の形（地面の高さと箱の一番下を足す）を変える。Frame Selected が `fitDistance` を共有することは保つ。
- **World に置く画像の板は、今のまま正面の目の高さに、視点に向けて立てて置く。** 板は底の無い絵で、立てて見るもの（オーナー、2026-10-17）。
- **開いたときの視点**（ADR 0045 の「出力の視点」）は、Camera が撮っていれば Camera、無ければ原点。向きは水平（pitch 0）から始める。パノラマは
  水平線が真ん中にあるときに最も自然に見え、地面が目より下にあるので水平に見てもグリッドが見える。
- **環境（`scene`）の調整は、状態に今ある位置・回転・大きさのまま持ち続ける。** UI はまだ無い。原点が足元の GLB の部屋や、傾いた 3DGS を地面や
  背景の水平線に合わせるのはこの調整の役目で、出すときは別に決める。大きさを置く物との相対で合わせたいときは、物の側を変える（オーナー）。

## まだ決めていないこと

- 「ここを地面にする」の操作の形と、地面の高さの見せ方。

## 考えた別案

| 案 | 選ばなかった理由 |
|---|---|
| World の原点を地面にし、撮った点を (0, 1.6, 0) の別の物（Eye）として持ち、`scene` を Eye に合わせて置く | Eye が視点・ERP の出力の位置・環境の錨を兼ね、別々に決められない。原点が足元の GLB の部屋は、床を合わせると目が地面に戻る。`scene` の位置は Keyframe を持てるので ERP の出力の位置が時間で動く。Pose handoff は受け取る側で判定し `sticker_state` は撮った点を持たないので、形式を変えるかノードごとに判定が食い違う。出力・形式・parity に広く触れるのに、得るのは数値の見た目だけ（独立レビュー、2026-10-17） |
| 開いたときに少し上・後ろから見下ろす（一般の 3D ツールの初期の視点） | 撮った点から見回すこのノードの体験が失われる。パノラマ由来の空間は撮った点から離れるほど崩れて見える |
| 原点から真下に光線を飛ばし、当たった所を床にしてグリッドを置く | 開くたび・内容が変わるたびに床が動く。対処療法（オーナー） |
| 少し見下ろす向きで開く | パノラマの水平線が傾いて見える。困っているのは物の置き場所で、視点の向きではない |
| 地面からの高さを別の数値としてインスペクタに出す | 高さの数値が二つになる（Working principles 1）。地面に置いた物の Y が -1.6 から始まるのは受け入れる |

## Consequences

- 状態に `ground` が加わる（parameter format の変更。JS はグリッドと置き方で、Python は `port` の 3D の Sticker の置き方で読む）。
- 地面に置いた物は、インスペクタの Y が `ground` の値（初期値 -1.6）から始まる。
- `docs/editor-interaction.md` の置く向きと 3D の Sticker を収めて置く式、`docs/threejs-spark-integration.md` の空間の表示（グリッドの高さ）、
  `docs/scene-state-v2.md`（`ground` の項目と、上流からの受け継ぎ）を直す。
- 後で World の数値を地面基準にしたくなっても、保存した位置を一斉にずらす移行で済み、この決定はそれを妨げない。
